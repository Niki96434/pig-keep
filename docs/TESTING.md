# Тестирование

## Особенности тестирования

### Backend:

Для изоляции интеграционных тестов используется отдельная, чистая тестовая БД.
Чтобы у тестовой бд была всегда актуальная структура в соответствии с закоммиченными миграциями, требуется воспользоваться командой:

```
npx drizzle-kit migrate
```

Для запуска интеграционных тестов проверки API с тестовой БД:

```
npm run test:api
```

Каждый it(...) проверяет один конкретный сценарий эндпоинта.

### Frontend:

При создании тестов для кастомных хуков для API каждый queryClient создавался заново
для изоляции кэша и успешного параллельного выполнения тестов без зависимости от глобального инстанса.
Тестировались только критическо важные части проекта, имеющие наибольшую ценность: чистые функции(юнит-тесты), кастомные хуки(юнит-тесты) и api+хук+компонент(интеграционные). Чистое тестирование деталей реализации приводит к хрупким тестам: такие тесты требуют поддержки при любом рефакторинге, но практически не ловят реальных багов приложения.

## Тестами покрыто:

- юнит-тестирование кастомных хуков(useEditNoteMutation.spec.tsx, useDeleteNoteMutation.spec.tsx, useCreateNoteMutation.spec.tsx)
  тестируют важные side-эффекты(инвалидацию кэша, передачу id/body, обработку ошибок)
- юнит-тестирование схем валидации Zod (validation.spec.ts)
  позволяют удостовериться, что схемы не сломаны, выполняются быстрее тестов через API.
- интеграционное тестирование бэкенд API: роутинг, статус-коды, сохранение в БД (api.spec.ts)
  проверяют всю цепочку: запрос -> хук -> состояние UI
- проверка открытия/закрытия формы при клике, валидация полей формы (NoteForm.spec.tsx)
- проверка отображения списка заметок, проверка на серверную ошибку при выводе списка (NoteList.spec.tsx)

## Запуск в CI автоматических тестов

- Реализовала запуск тестов фронтенда в отдельном CI пайплайне в Github Actions. Я использовала для этого скрипт `vitest run`, чтобы  CI-сервер не завис в бесконечном watch-режиме из-за отслеживания изменений кода. Порядок выполнения заданий зависел от времени выполнения от быстрого к долгому, таким образом в начале происходит запуск линтеров, затем только типы, тесты и сборка. С помощью `cancel-in-progress`
инфраструктура посылает сигнал SIGTERM/SIGINT для обрывания выполнения текущего пайплайна и выполняет новый без сбоев, что отлично подходит для экономии вычислительных ресурсов сервера и не уменьшает ожидание результата из-за очереди пайплайнов. По принципу наименьших привилегий добавлено свойство `permissions.contents: read`, чтобы защититься от вредоносного кода в npm-пакетах.
